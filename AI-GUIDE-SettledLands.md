## История инцидента: Build 257 ABI mismatch / Build 258 hotfix

Пользователь сообщил «вылет» на build 257. ## 0. Главное правило (после инцидентов 230 / 231 / 233 / 234 / 236)
**Нерабочий jar дороже, чем отсутствие jar.** Любая сборка проходит шлюз проверок
(§2) ДО выдачи. Если проверку провести нечем — сначала сделать инструмент, потом сборку.
Никаких «должно работать»: только «проверено вот этим скриптом, вот этот вывод».

## 1. Что нельзя проверить в песочнице и как это компенсировать
Нет `javac`, нет классов Minecraft/NeoForge, нет запуска игры. Значит:
* нельзя вручную вставлять байты в `Code` существующих классов (сдвиги → невалидный класс); допустим только проверенный пересчёт `classedit.py`/`smt.py` и JVM-шлюз;
* нельзя писать код «на глаз» без структурной валидации;
* Mixin/ASM-этап эмулируется только нашими парсерами → они должны быть строгими (§2).

## 2. ШЛЮЗ ПЕРЕД ВЫДАЧЕЙ (обязательно, каждый билд)
1. **Калибровка**: `python3 tools/validate_jar.py <прошлый рабочий jar>` → должно быть
   «ВСЕ ПРОВЕРКИ ПРОЙДЕНЫ». Если валидатор ругается на рабочий билд — сначала починить
   валидатор (ложные срабатывания так и ловятся).
2. `python3 tools/validate_jar.py <новый jar> --base <прошлый jar>` → «ПРОЙДЕНЫ» + дифф
   ровно тот, что задуман (лишних изменённых записей быть не должно).
3. `python3 tools/jvm_verify.py <jar> '<Class>#<method>' …` → «ИТОГ: OK» для КАЖДОГО
   изменённого класса. Это верификация настоящей JVM на синтетических заглушках
   (см. §11). Без неё правка `Code` не считается проверенной.
4. `python3 tools/selftest_probe.py` → допускается только «JVM-САМОТЕСТ: OK».
   Скрипт собирает **тот же** генератор, что идёт в jar, и грузит класс реальной JVM
   (`tools/jdkpkg/jdk4py/java-runtime/bin/java -Xshare:off`). Валидатора недостаточно:
   он проверяет структуру, но не верификацию JVM. Самотест обязан исполнять свой `main`
   и печатать ожидаемые маркеры (`selftest = A/B`, `obj = NULL`).
   Обязательно сверять, что байткод в jar == байткод, прогнанный самотестом
   (`build_probe_class(with_main=False)` vs `True` — должны совпадать кроме `main`).
5. `python3 tools/check_mixin_class.py <каждый новый самописный class>` → OK.
6. `tools/verify_jar.py <jar> --base ...` → zip/toml/lang/mixins/маркеры.
7. Только после этого — `present_file` (jar → zip → jar, чтобы основным остался jar) + sha256/размер + ссылка.
8. Отдельно: регресс-тест валидатора на заведомо сломанном jar, если он есть в репо
   (например `settledlands-0.8.0-build233-probe.jar` обязан валиться).
   Валидатор, который не ловит известный дефект, бесполезен.

Что именно проверяет `validate_jar.py` (весь jar, все классы):
структура до последнего байта; все индексы пула (this/super/interfaces/поля/методы/
атрибуты/операнды); операнды байткода по тегам; exception_table в границах кода; цели всех переходов (`if*`, `goto`, `tableswitch`,
`lookupswitch`) и `exception handler` — на границах инструкций;
полный разбор `Code`, `LineNumberTable`, `StackMapTable`, аннотаций, `SourceFile`,
`Signature`, `Nest*`, `InnerClasses`, `BootstrapMethods` и др.; версия 49..65;
миксины из JSON существуют; `@Mixin.value/targets` — массив.

## 3. Уроки по байткоду (дорого стоили)
* **Порядок сборки пула**: все `cp.utf8(...)` должны быть добавлены ДО `cp.dump()`.
  Инцидент 233: `SourceFile.sourcefile_index=79` при пуле 79 →
  `ClassReader.readUtf AIOOBE: Index 79 out of bounds for length 79` на скане NeoForge
  (игра падает ДО загрузки модов). Симптом в логе: `An error occurred scanning file Mod file: ...`.
* **Аннотации**: `@Mixin(value = X.class)` — это `Class<?>[]`, кодировать МАССИВОМ:
  `5b 0001 63 <utf8-дескриптор>`. Одиночный `63` → `ClassCastException: asm.Type -> Iterable`
  на `MixinInfo.readTargets` (инцидент 231). Форма `targets = {"..."}` — `5b 0001 73 <utf8>`.
  `method` (тег `s`) и `at` (тег `@`) одиночными работают — проверено на `GuideCorpseNameTagMixin`.
* **Не вставлять байты в `Code` вручную** (инцидент 230: AIOOBE на 11 миксинах).
  Допустимы правки равной длины и вставки только через `classedit.py`/`smt.py` с проверкой
  структуры, калибровкой и настоящей JVM, либо новый класс/миксин.
* Свой класс без ветвлений → `StackMapTable` не нужен (major ≥ 50).
  Свой класс С ветвлениями → либо major 49 (старый inference-верификатор), либо честные фреймы.
* `ldc` требует индекс ≤ 255 — следить, чтобы нужные записи пула не оказались дальше.
* `Component` в Minecraft 1.21 — интерфейс. Вызов его статического метода через `CONSTANT_Methodref` ведёт к `IncompatibleClassChangeError`; `invokestatic` на interface требует правильного InterfaceMethodref и версии класса ≥ 52. В major 49 build 238 уведомление создаётся через `new TranslatableContents(...)` + статический метод класса `MutableComponent.create`, как это делает vanilla `Component.translatable`. Проверять реальным исполнением, а не только верификацией.
* `Inventory.add(stack)` может при creative и заполненном инвентаре обнулить непоместившийся остаток, а boolean не доказывает полный перенос. Build 238 вставляет ограниченные порции в заведомо подходящий слот и сразу обновляет NBT `count`; сохраняет компоненты. `ItemStack.parse` использует `resultOrPartial` и может потерять частично разобранные модовые компоненты — при возврате использовать только полный `CODEC`/`DataResult.result()` и сохранять повреждённые записи.
* Vanilla `Entity.discard()` не делает смерть и сам по себе не возвращает привязанный поводок; 239 перед удалением использует тот же `GuideCorpseNpc.dropLeash(true, true)`, что и существующий `mobInteract`. Если список пуст на входе, это не успешный возврат: обычное тело не удалять. Для обнаружения преждевременного удаления нужны JVM-мутанты с неполным инвентарём, пустым телом и отключённым снятием поводка.
* UUID владельца + единственное тело поблизости не устанавливают, к какой смерти оно относится: рядом может быть старое тело. Build 241 записывает фактический UUID нового тела только после успешного спавна и копирует при клоне; старые/незагруженные тела не угадывает. Обычный алтарь при fallback всё равно расходует 9 по старому коду. Список ожидающих вещей имеет отдельную привязку к смерти: иначе старый список можно случайно выдать через новый труп. При конфликте двух списков сохранять оба, не объединять предполагаемые копии.
* Проверка `cult(npc) >= 1` сама по себе не защищала от вселения в неотмеченного NPC: раньше событие с HIGHEST-приоритетом копировало очки игрока в NPC до HIGH-проверки. Диагностировать весь путь и приоритеты событий; проверять отсутствие побочных записей по двум разным NPC и при положительных личных/общих очках. Build 240 отключает только handler моста; сохранённые ранее значения не мигрирует. JVM-fixture выполняет реальные методы на стендах, но не проверяет NeoForge event bus и игру.

## 4. Диагностика: сначала измерение, потом правка
* Сначала смотрим `latest.log` юзера (правило: сразу после «залил лог» — `git fetch origin`,
  `git checkout origin/main -- latest.log`, сверить версию мода в логе с тем, что выдавали).
* Если причина не доказана — собираем ЗОНД (только чтение), а не «ещё один фикс».

* Диагноз фиксируем в `SESSION-STATE.md` фактами из байткода/лога, а не гипотезами.

## 11. JVM-верификация на заглушках (главный инструмент)
`tools/jvm_verify.py <jar> 'dev/…/Class#method' ['…']`

Что делает: генерирует классы-заглушки для всех внешних типов (net/minecraft,
org/slf4j, …), подсовывает их JVM вместе с настоящим jar и вызывает метод через
рефлексию. Класс загружается без инициализации, метод разрешается по точной сигнатуре; `DECLARED` обязателен для каждой цели. `VerifyError`/`ClassFormatError` = провал, ошибка ДО `DECLARED` = непроверено. Ошибки вызова на синтетических заглушках после `DECLARED` не являются игровым тестом.

Калибровка (обязательно повторять после правок инструмента):

| jar | ожидание | факт |
|---|---|---|
| 230, `GuideNpc#applyProfile` | VerifyError | `Bad instruction` (неинициализированная локаль) |
| 234, `TexProbe#logObj(java.lang.String,java.lang.Object)` | VerifyError | `Illegal target of jump or branch` |
| 232/236, `GuideNpc#applyProfile` | OK | OK |
| 235, `TexProbe#logObj(java.lang.String,java.lang.Object)` | OK | OK |

Правила работы с `Code` (дополнение к §3):
* вставка обязана быть **кратна 4** (switch-и выравниваются от абсолютного адреса);
* `invokeinterface`: count = objectref + слоты аргументов;
* после вставки пересчитываются: переходы, `exception_table`, `LineNumberTable`,
  `StackMapTable` — `tools/classedit.py` + `tools/smt.py` (фреймы пересобираются
  с сохранением типов, меняется только delta);
* пересборка пула проверяется байт-в-байт (`patch_pool`) — если не совпала, сборка
  останавливается.

## 12. «Вылет» после раздачи: сперва проверить САМ ФАЙЛ
Порядок разбора (инцидент 27.10.2026, build 236):
1. `git fetch origin` → забрать новый `latest.log`.
2. Искать `is not a jar file`, `zip END header not found`, `UnionFileSystem`.
   Это **не баг мода**, это недокачанный файл. Не пересобирать, а дать
   PowerShell-команду `Invoke-WebRequest -OutFile` + сверку `Length` и `sha256`.
3. Только если jar на месте и валиден — смотреть дальше (VerifyError, FATAL).
Своя сторона тоже проверяется: `python3 -c "import zipfile;zipfile.ZipFile(p).testzip()"`,
наличие `PK\x05\x06`, размер = размер на GitHub (`gh api ... --jq .size`).
Битый скачанный файл лечится удалением из `mods` и повторной закачкой — не правкой кода.
