# Инструкция для ИИ-ассистентов: разработка, пропатчивание и верификация Minecraft NeoForge модов

Практическое руководство для ИИ-агентов, работающих над модификациями **Minecraft (NeoForge 1.21.1 / Java 21)** — как при наличии полного Gradle-проекта, так и при точечном пропатчивании уже собранного `.jar` без исходников/Gradle.  
Собрано на основе реальных ошибок и практик проектов `SettledLands` (430+ сборок) и `Hackers 'n Slashers` (`v1–v6`).

---

## 1. Золотые правила перед началом работы

1. **Компиляция с `exit 0` НЕ означает рабочий мод.**  
   В изолированной песочнице без запущенного клиента/сервера Minecraft компилятор видит только то, что ему подложили на `-cp`. Любой выдуманный метод, потерянная аннотация, неверный `Mixin`-дескриптор или пропущенный файл в JAR дадут краш при запуске или молчаливый отказ в игре.
2. **Никогда не угадывать API Minecraft, NeoForge или сторонних модов.**  
   Нельзя опираться только на память об API (сигнатуры 1.19 / 1.20.1 / 1.21.1 и Forge vs NeoForge отличаются!). Каждый внешний класс, метод и поле должны быть подтверждены:
   - либо реальным `.jar` / исходниками целевой версии;
   - либо дизассемблированием классов рабочего базового мода;
   - либо проверенными стабами/справочниками в репозитории.
3. **Сначала аудит, потом правки.**  
   Перед началом работы проверить целевой JAR, `META-INF/neoforge.mods.toml`, `*.mixins.json`, конфиги, JSON-анимации и датапаки. При наличии модов-компаньонов (Better Combat, Punchy, PlayerAnimLib и др.) — дизассемблировать и их точки пересечения, а не додумывать их логику.
4. **Побайтовая сохранность и чистота дерева.**  
   Не держать мусорные/устаревшие стабы на рабочем classpath, сохранять полный пакет изменённых исходников в `*-Source.zip`, фиксировать `SHA-256`.

## 2. Два сценария сборки

### Сценарий A: Есть полный Gradle-проект (`build.gradle` + `gradlew`)

1. Проверить целевую версию Java/MC/NeoForge (`Java 21` = classfile `major 65` для MC 1.21.1), маппинги (`Mojmap` + `Parchment`).
2. Проверить дерево исходников (`src/main/java`, `resources`, `*.mixins.json`, `neoforge.mods.toml`) на соответствие последнему рабочему эталону.
3. Собрать `./gradlew build` (или проектный скрипт сборки).
4. Прогнать **все** статические и runtime-проверки (раздел 4) уже по **итоговому JAR**, а не по промежуточному каталогу классов.

### Сценарий B: Пропатчивание готового `.jar` без исходного Gradle-проекта

Когда доступен только `.jar` мода (и при необходимости `.jar` модов-компаньонов), безопасный конвейер выглядит так:

1. **Распаковка и анализ (Read-Only):**
   - Сохранить неприкосновенную эталонную копию оригинального `.jar` (например, `/tmp/inspect/orig.jar`) — она пригодится как `--base` для аудита ссылок.
   - Дизассемблировать целевые классы (`javap`, `tools/disasm.py`, `tools/classfile.py`), прочитать все `*.mixins.json`, `neoforge.mods.toml`, JSON-анимации/пресеты.
   - Выписать **точные** дескрипторы всех методов и полей, с которыми придётся взаимодействовать.

2. **Подготовка окружения компиляции (ECJ + базовый JAR):**
   - Использовать Java 21 и компилятор `ecj` с флагами `-21 -proc:none`.
   - На `-cp` подавать **два непересекающихся слоя**:
     1. Скомпилированные минимальные стабы **только внешних** библиотек (`net.minecraft.*`, `net.neoforged.*`, `org.spongepowered.asm.*`, библиотеки вроде `playeranim`/`bettercombat` и т.д.).
     2. Рабочий **базовый JAR мода**, из которого ECJ резолвит все классы самого мода с реальными сигнатурами.
   - **Критическая ошибка (не допускать!):** нельзя держать стабы классов самого мода в одном classpath с базовым JAR — возникнут конфликты типов либо ECJ скомпилирует вызов против неточного стаба, что вызовет `NoSuchMethodError` / `NoSuchFieldError` в игре.

3. **Точечная перекомпиляция и переупаковка:**
   - Перекомпилировать **только** изменённые и вновь добавленные `.java` файлы.
   - **Не перекомпилировать без нужды** нетронутые классы (особенно классы с лямбдами `lambda$...`, сериализаторами/пакетами NeoForge и конфигами) — иначе можно потерять/изменить сгенерированные компилятором имена или сигнатуры.
   - Взять рабочий базовый JAR и перезаписать в нём **только** заново скомпилированные `.class` + обновлённые конфиги/ресурсы (например, `*.mixins.json`), сохранив все остальные записи JAR побайтово без изменений.

## 3. Критические подводные камни NeoForge, Mixin и байткода

### 3.1. Аннотации при восстановлении существующего класса
Если существующий класс мода пришлось восстановить из байткода и перекомпилировать:
- Обязательно сравнить `RuntimeVisibleAnnotations` и `RuntimeInvisibleAnnotations` в **оригинальном** и **новом** `.class`!
- Типичные смертельные потери:
  - `@EventBusSubscriber(modid = "...", value = Dist.CLIENT)` — в NeoForge `value` имеет тип `Dist[]`. Если перепутать с устаревшим `bus = Bus.MOD/GAME` или потерять `Dist.CLIENT`, обработчики событий перестанут регистрироваться либо сервер упадёт при загрузке клиентских классов.
  - `@SubscribeEvent` — пропажа аннотации = метод больше не вызывается вообще, без единой ошибки в логе.
  - `@OnlyIn(Dist.CLIENT)` / `@Mixin(...)`.

### 3.2. Mixin: частые причины крашей
1. **Незарегистрированный миксин:** класс добавлен в JAR, но забыт в `*.mixins.json` (или наоборот — указан в JSON, но отсутствует в JAR).
2. **Неверная секция `*.mixins.json`:** клиентский миксин (обращающийся к `Minecraft`, `LocalPlayer`, `ItemInHandRenderer`, `Camera`, `HumanoidModel`) **обязательно** в `"client": [...]`, никогда не в `"mixins": [...]`, иначе выделенный сервер упадёт при старте.
3. **Коллизии имён в общих target-классах:** если к одному классу игры (например `ItemInHandRenderer` или `LivingEntity`) прицеплено несколько миксинов из одного или разных списков, добавляемые вспомогательные методы обязаны иметь уникальный префикс (`modid$helperName`), иначе Mixin-трансформер выдаст конфликт слияния.
4. **Безопасная совместимость с опциональными модами (Punchy, Better Combat, MallardGuard и др.):**
   - Подключать совместимые миксины через `IMixinConfigPlugin.shouldApplyMixin`, проверяя `LoadingModList.get().getModFileById("targetmod") != null`.
   - Помечать целевые миксины опционального мода `@Pseudo`, а runtime-логику выносить в изолированный `*ClientBridge` с проверкой `ModList.get().isLoaded(...)` и защитой от отсутствующих классов (`Throwable`).
5. **Осторожность с частыми `@Inject(TAIL)` на контроллеры анимаций:**  
   Нельзя каждый тик затирать/останавливать слой после вызова `replaceAnimationWithFade(...)` в оригинальном методе — анимация будет перезапускаться с фейдом 20 раз в секунду. Управлять запуском/остановкой нужно **до** или **вместо** запуска нового фейда в точке принятия решения.

### 3.3. Дескрипторы, маппинги и NeoForge 1.21.1
- Проверять точные сигнатуры на 1.21.1:
  - Пример: в 1.21+ `ItemStack.isSameItem(a, b)`, `ItemStack.getUseDuration(LivingEntity)` (или `(ItemStack, LivingEntity)` — проверять по JAR!), `ResourceLocation.fromNamespaceAndPath(...)` / `ResourceLocation.parse(...)` (в 1.21 конструктор `new ResourceLocation(...)` приватный!).
  - В NeoForge 1.21.1 классы Mojmap не обфусцированы, но старый код из Forge 1.20 часто ссылается на переехавшие пакеты (`net.minecraftforge` -> `net.neoforged`, `PacketDistributor`, `StreamCodec`, `PlayerAnimationAccess`).
- **Сетевые пакеты и инвентарь:** никогда не сериализовать крупные графы/структуры в NBT `ItemStack` через клиентский creative-пакет (лимит пакета ~2 МБ и риск `DecoderException`) — передавать минимальный ID, копировать данные на сервере.

### 3.4. Отладка 1st-person анимаций, камеры и 3D-поз
1. **Не подбирать углы и координаты «вслепую»!**  
   При изменении поз рук/предметов в 1st-person (особенно в PlayerAnimLib / PAL) проверять итоговую матричную цепочку от корня камеры:
   - Порядок трансформаций в PAL: `ItemInHandLayerMixin` / `PlayerRendererMixin` / модификаторы (`FirstPersonCameraModifier` -> кастомный модификатор через `addModifierBefore`) / `PoseStack` предмета в руке (`XP(-90°)` для предмета в руке, зеркалирование X для левой руки и т.д.).
   - Писать небольшой 3D-проекционный скрипт (Python), подставляющий реальные числа из JSON-анимации и модификаторов с учётом `FOV` (80°–100°), `pitch` игрока и приседания (`crouch`), чтобы заранее видеть экранные координаты углов щита/оружия и не перекрыть прицел или не вывернуть предплечье в экран.
2. **Не дублировать модификаторы камеры/приседания:**  
   Если в стеке уже есть модификатор, сдвигающий `left_arm.posY` при приседании или ходьбе (например, `FirstPersonCameraModifier`), новый модификатор не должен добавлять тот же сдвиг второй раз.
3. **Сброс интерполяторов при возврате из паузы/простоя:**  
   Если модификатор пропускал кадры (например, 1P-слой был остановлен ради Punchy idle), при повторном включении `smoothBlend` обязан сбрасываться в `0.0F` (`onYieldToIdle()` + защита по `lastPlayerId` и длинной паузе `nowNs - lastStepNanos`), чтобы предмет плавно поднимался с нуля, а не «телепортировался» в последний сохранённый кадр. И проверять порог схождения (`Math.abs(blend - target) < 0.001F` -> присваивать `target`, **а не `0.0F`**!).

## 4. Обязательный конвейер верификации перед отправкой пользователю

Перед передачей любого `.jar` пользователю необходимо пройти **все 6 уровней проверки** (`tools/`):

### Уровень 1 — Структура JAR (`validate_jar.py`)
```bash
python3 tools/validate_jar.py <mod.jar> --expect-version <version>
```
Проверяет целостность ZIP, читаемость `META-INF/neoforge.mods.toml`, точный `modId` и `version`, валидность всех `*.mixins.json` и физическое наличие каждого заявленного класса миксина внутри JAR.

### Уровень 2 — Валидация байткода (`jvm_verify.py`)
```bash
python3 tools/jvm_verify.py <mod.jar> --target-major 65
```
Проверяет каждый `.class` в архиве: корректная структура constant pool / атрибутов, `class version <= 65` (Java 21).

### Уровень 3 — Проверка внешних API и конфликтов миксинов
```bash
python3 tools/check_mixin_class.py <mod.jar> --base <working_base.jar>
python3 tools/mixin_clash_check.py <mod.jar>
```
- `check_mixin_class.py --base ...` гарантирует: в новом JAR **ноль** новых непроверенных вызовов Minecraft/NeoForge/сторонних модов относительно уже работающего в игре базового JAR (если появился новый внешний вызов — он должен быть отдельно подтверждён по целевому JAR/API).
- `mixin_clash_check.py` гарантирует отсутствие коллизий имён методов в миксинах, разделяющих один target-класс.

### Уровень 4 — Отсутствие «битых» ссылок (`dangling_refs.py`)
```bash
python3 tools/dangling_refs.py <mod.jar> --base <orig_base.jar>
```
Гарантирует `0 dangling references`: ни один класс не ссылается на метод, поле или внутренний класс, которые были удалены/переименованы при пропатчивании (защита от `NoSuchMethodError` / `NoSuchFieldError`).

### Уровень 5 — Побитовый аудит аннотаций и пула констант изменённых классов
Для каждого пересобранного существующего `.class`:
- Сравнить список методов и их дескрипторов с базовым классом.
- Проверить `RuntimeVisibleAnnotations` / `RuntimeInvisibleAnnotations` на уровне класса и методов.
- Вывести `Added refs` / `Removed refs` между старым и новым пулом констант — убедиться, что не утекли синтетические или тестовые классы и не исчезли нужные вызовы.

### Уровень 6 — Реальный прогон под HotSpot `-Xverify:all`
```bash
java -Xverify:all -cp <patched_classes_from_jar>:<mocks_and_stubs> VerifyProbe
```
Обязательно:
- Загрузить и инициализировать **именно байты из финального `.jar`** под жёстким верификатором байткода HotSpot `-Xverify:all` (проверяет `StackMapTable`, типы на стеке операндов, инициализацию статиков).
- Прогнать сценарные unit-пробы:
  - основной рабочий сценарий и переходы состояний (idle -> действие -> возврат -> повторное действие);
  - сходимость численных модификаторов (нет скачков, нет сбросов на границе, нет двойных сдвигов);
  - альтернативные ветки (левая главная рука, отсутствие опциональных модов, граничные `null`/пустые `ItemStack`).

## 5. Упаковка, хэши и правила доставки результата

1. **Артефакты в комплекте:**
   - Финальный `*.jar` мода.
   - Архив изменённых/добавленных исходников `*-Source.zip` (чтобы следующий разработчик или агент мог продолжить работу без повторного дизассемблирования).
   - Файл контрольных сумм `*.sha256sums.txt`, проверенный командой `sha256sum -c`.
   - Актуальный `README` на языке пользователя со списком изменений и рекомендациями по проверке в игре.
2. **Контроль версий (если работа в Git-репозитории):**
   - Проверить `git status` — не оставлять временный мусор из `/tmp` или гигантские бинарники вне правил репозитория.
   - Зафиксировать коммит и запушить в текущую активную ветку.
3. **Передача пользователю:**
   - Показать основной артефакт через `present_file`.
   - Если используется Google Drive — загрузить `*.jar`, `*-Source.zip` и сопутствующую документацию в нужную папку и выставить публичный доступ для скачивания.
   - В ссылках на GitHub использовать **только прямые ссылки скачивания** (`.../raw/<branch>/<file>`), а не ссылки просмотра (`/blob/...`).
   - В финальном ответе: кратко и по делу описать сделанные изменения на русском языке, указать что именно протестировано автоматически, а что требует проверки в самой игре, привести SHA-256 и дать прямую ссылку на скачивание в самом конце сообщения (без лишних логов и кода после ссылки).
