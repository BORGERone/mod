# Settled Lands — сборка 375 (door-client)

Файл мода: `settledlands-0.8.0-build375-door-client.jar`
Версия в игре: `0.8.0-build375-door-client`
Собрано из базы: `settledlands-0.8.0-build374-door-proof.jar`

## Где был этот тик

Не в двери. В клиенте.

Я проверил патчи NeoForge для 1.21.1 — метод, который решает, дойдёт ли клик до блока, выглядит так
(`MultiPlayerGameMode#performUseItemOn`):

```java
PlayerInteractEvent.RightClickBlock event = CommonHooks.onRightClickBlock(...);
if (event.isCanceled()) {
    return event.getCancellationResult();   // <- только это останавливает локальное открытие
}
```

А мой обработчик начинался со строки

```java
if (!(level instanceof ServerLevel server) || pos == null) return;
```

На клиенте `level` — это `ClientLevel`, значит обработчик выходил сразу, **событие не отменялось**, и
клиент спокойно выполнял `DoorBlock#useWithoutItem` у себя локально. Дверь на экране открывалась на тик
(пока не придёт ответ сервера), и упёршийся игрок в этот тик проскакивал. Сервер при этом всё это время
молчал — он-то отказывал, но клиенту об этом никто не говорил.

Ответ на вопрос «почему 373 и 374 не помогли»: они закрывали сервер и саму дверь, а картинку рисовал
клиент, которого никто не спрашивал.

## Что сделано в 375

**Клиент больше не открывает двери сам.** На любой клик по двери клиент отменяет событие
(`setCanceled(true)` + `InteractionResult.SUCCESS`) и ничего не делает локально. Решает сервер:

- **незапертая дверь** — сервер открывает её как обычно и присылает состояние; вы видите открытие на
  один тик позже (в одиночной игре это незаметно);
- **запертая дверь** — сервер отказывает (отказ из 373), дверь не открывается ни на сервере, ни на
  клиенте, и нарисовать её открытой больше некому;
- клик всё равно доходит до сервера: пакет `ServerboundUseItemOnPacket` отправляется **до** локального
  предсказания, поэтому открытие незапертых дверей и работа ключа не страдают.

Дополнительно в лог пишется одна строка, когда клиент впервые отказал:
`door: the client refused to open the door at <позиция> on its own - only the server opens doors now (build 375)`.
Строка из 374 (`DoorBlock#useWithoutItem was reached … locked=<true|false>`) тоже осталась.

## Что проверить

1. Запустить, убедиться, что в `latest.log` нет `Failed to create mod instance` (иначе сессия негодная —
   перезапустить, не кликая мышью на экране загрузки).
2. Обычная дверь: ПКМ — открывается и закрывается как раньше.
3. Запереть дверь ключом, **упереться в неё и быстро кликать** — дверь не должна открываться ни на кадр.
4. Ключ по запертой двери — снимает замок (и по-прежнему не открывает её).
5. Моб не ломает запертую дверь; проводник НПС проходит через неё и закрывает за собой.

## Как читать лог, если тик останется

- `the client refused to open the door …` есть, а дверь всё равно мигает — значит открывает не клик
  игрока (другой мод, контрапция, редстоун), пришлите лог, разберу по строке.
- строки `the client refused …` нет — клиентский отказ не сработал (например, событие не доходит),
  это видно сразу.
- `DoorBlock#useWithoutItem was reached … locked=false` — замок не найден на этой позиции.

## Что не подтверждено в игре

- Поведение проверено только на уровне кода и гейтов: в игре эта сборка ещё не запускалась.
- Незапертые двери теперь открываются сервером, без клиентского предсказания: в одиночной игре это
  один тик, на удалённом сервере — до RTT.
- Двери, которые не являются `DoorBlock` (створки Create, Supplementaries и т. п.), этим правилом не
  затрагиваются.
