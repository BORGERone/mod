# Сборка 401 — сначала реплика, потом сундук; дверь «открытие» говорит; ESC закрывает панель

**Версия:** `0.8.0-build401-chain-first`
**База:** 400 (`settledlands-0.8.0-build400-chest-open.jar`)
**Файл:** `settledlands-0.8.0-build401-chain-first.jar` (603 записи, 553 класса, 3 642 737 B)

---

## Три твоих отчёта

1. «порядок: сначала реплика, потом инвентарь» — сейчас наоборот;
2. «дверь: при открытии двери проиграется реплика, но сейчас ничего не происходит»;
3. «проблемы с закрытием взлома на ESC, срабатывает через раз».

И одна находка, которая нашлась по дороге и объясняет, почему часть всего этого вела себя как «ничего не
происходит». Начну с неё, потому что она — причина, а остальное — следствия.

---

## 0. Почему обработчики кликов умирали на первом же обращении к событию

У меня есть «зеркала» ванильных классов — маленькие копии, по которым код компилируется (в игру они не
попадают). Одно такое зеркало было **неправильным**:

```java
// было, четыре сборки подряд
public class PlayerInteractEvent {
    public Entity getEntity() { return null; }   // ← такого метода в игре НЕТ
```

В игре `getEntity()` у этого события объявлен в `PlayerEvent` и возвращает **`Player`**. Значит у метода
существует ровно один дескриптор — `()Lnet/minecraft/world/entity/player/Player;`. А мой код после
компиляции просил `()Lnet/minecraft/world/entity/Entity;`.

Такой вызов не ломает запуск и не ломает загрузку класса. Он падает **на первом клике** —
`NoSuchMethodError`, внутри `try` самого обработчика. То есть обработчик начинался и умирал на первой строке:

| Класс | Что не работало |
|---|---|
| `ChestGraph396Events#onUse` | падал на `event.getLevel()` — **до** проверки замка и **до** чтения «взлома» |
| `DoorEvents368#onRightClick` | падал на `event.getEntity()` — до сообщений и до цепочки |
| `DoorGraph382Events#onRightClick` | падал так же (палочка по двери) |
| `BlockTriggerEvents351#onRightClick` | падал так же (клик по блоку-триггеру) |

И то же самое с `BlockEvent#getLevel()`: у него в игре тип `LevelAccessor`, а зеркало говорило `Level`.
Из-за этого не работали охранники «сундук нельзя разбить» и «дверь нельзя разбить».

Это и есть причина твоего второго отчёта в самой простой форме: **цепочка не запускалась, потому что
обработчик, который должен был её запустить, падал раньше**. И причина того, почему в 400-й «порядок был
неправильный»: клик по сундуку до `onUse` не доходил, «взлом» не записывался, и цепочка запускалась
единственным оставшимся путём — при **закрытии** окна, то есть уже после того, как инвентарь открылся.

**Исправлено:** зеркала приведены к игре (`Player`, `LevelAccessor`), четыре класса перекомпилированы.
И добавлен 35-й гейт `tools/event_getter_check.py`, который ловит именно это: он требует, чтобы к одному
геттеру одного события весь jar обращался **через один дескриптор** — и код мода, и код базового мода
(базовый мод скомпилирован против настоящего NeoForge, поэтому он и был доказательством). На 400-й гейт
падает ровно на `getEntity` и `getLevel`, на 401-й — зелёный.

## 1. Сундук: реплика → окно

**Было (400):** панель решена → панель закрывается (когда отпущены клавиши) → `onClose` щёлкает по
сундуку → сундук открывается. Цепочка под узлом «взлом» запускалась позже, при закрытии окна. Отсюда
«сначала инвентарь, потом реплика».

**Стало (401):**

1. Клик по сундуку больше **не** принадлежит панели. Панель вообще не щёлкает (`HackPanel377` этого
   больше не делает).
2. Сервер получает ответ панели и делает всё в правильном порядке:
   * ставит «взлом» — `ChestLock397.crack(кто, ключ)`. Теперь это **ключ из игрока и сундука** и живёт
     **10 минут**, а не 10 секунд на всех: реплику читают в своём темпе, а десяти секунд 400-й не хватало;
   * **прогоняет цепочку** под узлом «взлом» (`ChestGraph396#runCrack` → `BlockTrigger351#startReportingWindow`);
   * цепочка сама сообщает, остановило ли её окно (реплика / кнопки / катсцена) — новый флаг `stopped[0]`;
   * и только после этого отправляет клиенту `settledlands:chest_ready` («сундук готов к клику», и ждать ли
     окна).
3. Клиент (`ChestOpen401`, тик через `ChestOpenWatch401`) держит клик, пока окно цепочки не закрыто и пока
   экран не пуст **два тика подряд** (два, а не ноль: цепочка может поднять следующее окно в том же кадре).
   Дальше — тот самый штатный `useItemOn`, который в 400-й сработал.
4. Пока окно открыто, `chest_ready` ждёт; если окно почему-то не пришло за 5 секунд, клик всё равно
   доставляется. Если клик не удался за минуту — запрос забывается и хватает одного твоего клика (замок
   «взлома» живёт 10 минут).
5. В action bar теперь «Замок снят: сундук откроется сам» (было «нажми на сундук ещё раз» — этого больше не
   требуется).

Дополнительно: `ChestGraph396Events` больше **не** запускает цепочку «взлом» при закрытии окна (иначе она
сыграла бы второй раз). Обычное открытие сундука по-прежнему запускает «открытие» при закрытии окна.

## 2. Дверь «открытие»: две ноги вместо одной

**Было:** единственный триггер цепочки — `@Inject` в `RETURN` метода `DoorBlock#useWithoutItem`
(`DoorUse373Mixin`), и он с `require = 0`. `require = 0` означает: «если селектор не совпал с этой версией
игры — не падай, просто не вставляйся». Миксин, который не вставился, и провод, к которому ничего не
подключено, выглядят из игры **одинаково**: ничего не происходит.

**Стало:**

* **Нога первая (миксин)** — как была, и теперь она **пишет в лог**, что жива: одна строка при первом
  использовании двери (`DoorUse373Mixin is LIVE`), одна при переходе «была закрыта → стала открыта».
* **Нога вторая (без миксина)** — игровое событие `PlayerInteractEvent.RightClickBlock` (его миксином не
  убрать): клик по **закрытой** двери передаёт дверь в `DoorSignal398#watch`, и через тик дверь читается
  снова. Была закрыта, стала открыта — значит открыл этот клик, цепочка запускается. Если дверь осталась
  закрытой — в лог уходит строка «клик по закрытой двери её не открыл», без шума.
* **Ноги не дублируют друг друга:** общая защита в четверть секунды (`GUARD_MS`). Если миксин сработал,
  вторая нога через полтика молча отказывается.
* **Молчания больше нет:** каждая причина, по которой цепочка может не пойти, пишется один раз с причиной —
  «у двери нет ключа», «у двери нет графа — палочкой её никто не открывал», **«на карточке у узла
  "открытие" ничего не подключено»**. Последняя строка и есть ответ на второй скриншот, если дело было не в
  дескрипторе: она прямо скажет, что провод не сохранился.

## 3. ESC на панели взлома

**Было:** решённая панель закрывается сама, когда все клавиши отпущены. Аварийный выход по ESC ждал
**удержания 1200 мс**, и время считалось по событиям `keyPressed` — то есть по **повторам** клавиши. Повторы
приходят «через раз» (это дело оконной системы, а не игры), поэтому удержание иногда не начиналось, иногда
заканчивалось само, и панель то закрывалась, то нет. Плюс сама панель успевала закрыться по «все клавиши
отпущены» — и это читалось как «срабатывает через раз».

**Стало:**

* удержание считается в `tick()` и в `render()` по **железу** — `InputConstants.isKeyDown(window, ESC)`;
  два места, потому что тик экрана — дело игры, а кадр — нет (пусть будет две попытки за кадр);
* удержание **800 мс** вместо 1200;
* пока держишь — панель пишет «ESC: 37% — панель уйдёт», то есть видно, что клавиша живая (удержание,
  которое измеряется, но не рисуется — это тот же «через раз»);
* в `keyPressed` ESC больше ничего не считает: он только гасится, чтобы игра его не увидела;
* уход по ESC **не теряет** решённое состояние: ответ уже на сервере, «взлом» уже поставлен;
* панель **не отправляет ответ повторно** (`settledlands$askAgain` теперь только пишет в лог). Повтор
  прогнал бы цепочку «взлом» второй раз — а она теперь идёт **до** открытия сундука.

## Что не изменилось (проверено)

* 400: настройки карточки сундука (числа/скорость/сложность) доходят до панели — проба гоняет настоящий код
  jar: `CARD_AFTER keys=9 sec=3 diff=2`;
* 399: графы открываются, слово тумблера меняется сразу, синий узел карточки тянется, вторые узлы
  «взлом»/«открытие» на месте;
* 398: твой взлом заканчивается открытым инвентарём сундука (теперь — после реплики);
* 395: дверь после взлома не закрывается в лицо; 393: диалог после взлома; 392/394: узлы на холсте и
  радиус.

## Проверки

* `verify_jar --base 400` — **PASS**: 603 записи, 553 класса, 9 заменено, 4 добавлено, 0 висячих ссылок,
  новых внешних обращений к API — **0** (`Screen#tick()` — единственный новый член, он внесён в
  `CONFIRMED_EXTERNAL` с цитатой из javadoc 1.21 NeoForge);
* **35 гейтов** `tools/*_check.py` — все зелёные (34 прежних + новый `event_getter_check`);
* `mixin_clash_check` — зелёный (195 хелперов в 67 миксинах, одно документированное исключение);
* **новая проба** `tools/harness/ChestOpen401Probe.java` гоняет настоящие классы jar:

```
CRACK_BEFORE false
CRACK_ONE true               ← «взлом» читается для того, кто решил панель
CRACK_OTHER false            ← и не читается для другого игрока на том же сундуке
CRACK_SPENT cracked=true take1=true take2=false   ← тратится ровно на один клик
ARM_BEFORE false
ARM_READY true               ← клик взводится словом сервера
ARM_CLEARED false
WATCH_QUIET ok               ← один тик без запроса — не исключение
```

* порядок «цепочка → `chest_ready`» проверяется **по байткоду** `ChestNet397#solve` (гейт сравнивает
  позиции двух вызовов в потоке инструкций, а не наличие в пуле констант — на пуле констант порядка нет);
* `event_getter_check` на 400-й **падает** на `getEntity`/`getLevel` — то есть новый гейт действительно
  ловит найденную причину, а не просто зелёный.

## Чего я не видел в игре

Игру я не запускаю. По первому отчёту причина установлена: обработчик `onUse` падал на первом обращении к
событию — это видно по байткоду 400-й сборки (дескриптор `Entity` против `Player`), и это ровно то, что
описывает симптом. По третьему отчёту ESC теперь читается с железа — тут гадать не о чем.

Если после этой сборки дверь всё ещё молчит — в `logs/latest.log` будет одна из двух строк:

* `door: DoorUse373Mixin is LIVE` — миксин вставился, значит дело не в нём (и рядом будет причина);
* `door: the «открытие» chain did not run for this click - the card of <ключ> has nothing wired to its
  «открытие» socket` — провод на карточке не сохранился;
* ни одной из них — миксин не вставился, работает вторая нога, и она скажет своё.

## Установка

1. Убери из `mods` 400-ю и положи `settledlands-0.8.0-build401-chain-first.jar`.
2. Сундук: граф сундука → сундук «взлом» → «Реплика #1» → сохрани. Взломай: сначала реплика, потом окно.
3. Дверь: дверь «открытие» → «Реплика #1» → сохрани. Открой дверь обычным кликом.
4. ESC на панели: держи 800 мс (панель показывает процент), отпусти — панель уйдёт.
