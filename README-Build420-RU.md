# Сборка 420 — якорь: графы постройки едут внутри схематика

**Версия:** `0.8.0-build420-graph-anchor`
**База:** 419 (`settledlands-0.8.0-build419-esc-immediate-close.jar`)
**Файл:** `settledlands-0.8.0-build420-graph-anchor.jar` (625 записей)
**sha256:** `19d5f064c9150dd401dc854e27d0c3e4d9d33a24654396a1fd11f9eca9847133`

---

## Что было не так

Жалоба автора: **«в этих схематиках не копируются графы блоков»**. Скопировать их было нельзя в принципе:
графы блоков, дверей и сундуков лежат не в блоках, а в мировых файлах
`settledlands_block_triggers`, `settledlands_door_graphs`, `settledlands_chest_graphs` и
`settledlands_doors` — и лежат **по абсолютным координатам**. Axiom (как и WorldEdit, Litematica,
структурный блок) переносит блоки и block entity с их NBT, но про эти файлы ничего не знает: после
вставки постройки на новом месте графов нет.

**Мостик в самом Axiom невозможен** — это проверено по его публичному API и по документации:
`AxiomClientAPI` (15 классов, `com.moulberry.axiomclientapi`) даёт только `CustomTool`, `BlockRegion`
(запись), `ToolService` (райкаст, состояние блока, потоки) — **ни буфера обмена, ни `.bp`, ни чтения
выделения**. Серверный хук существует только как Paper-плагин (`axiom:marker_data` и др.) и из NeoForge
недоступен. А вот NBT блоков и сущностей Axiom **копирует** — на этом и стоит решение.

## Как это работает (вариант C — якорь-маркер)

Одна невидимая сущность на постройку. Это **не новый блок и не новый entity type**, а уже существующий
в моде `settledlands:guide_trigger` — тот самый невидимый триггер. Он находится **по NBT, которое несёт**,
а не по имени и не по UUID, поэтому переименование сущности копировальным инструментом ничего не ломает.

Внутри маркера (`getPersistentData()`):

```
SettledLandsAnchor   = 420                  // версия раскладки
Graphs = [ { K: "block"|"door"|"chest",     // вид графа
             Off: [dx, dy, dz],             // смещение ОТ МАРКЕРА, не от мира
             G: <граф>,                     // сам граф, как он лежит в своём файле
             Lock: [ { Off: [dx,dy,dz] } ] } ]   // замки двери (только для дверей)
FP    = [ { Off: [dx,dy,dz], B: "minecraft:oak_planks" } ]   // отпечаток: 9³ куб, воздух выброшен
SettledLandsAnchorAt = [x, y, z, turn]      // где маркер уже разложил свои графы и с каким поворотом
```

Всё хранится **относительно маркера**, поэтому любое копирование сущностей с NBT несёт графы с собой.

### Четыре автоматических шага (каждые 40 тиков = 2 секунды)

1. **Ничего, пока нет игроков** — сервер без игроков не обслуживает никого.
2. **Освежение (`refresh`)**: у каждого маркера с графами в радиусе 48 блоков от игрока список графов
   пересобирается из четырёх файлов вокруг него (радиус сбора `GATHER_BLOCKS` = 24). То есть в схематик
   попадает то, что автор **построил**, а не то, что было на момент появления маркера.
3. **Автоустановка (`ensureAnchors`)**: если рядом с игроком есть графы, а маркера в радиусе 32 блоков нет —
   маркер ставится сам в **ближайшую свободную клетку** (проверка `BlockState.isAir()`). Автор ничего не
   размещает руками. Если свободной клетки нет — в лог и в чат уходит сообщение, мир не трогается.
4. **Раскладка после вставки (`materialiseIfMoved`)**: маркер, чей `SettledLandsAnchorAt` не совпадает с
   его текущей позицией, был **вставлен копировальным инструментом**. Его записи раскладываются по
   четырём файлам по формуле `позиция_маркера + повёрнутое_смещение`, замки дверей — через `DoorStore368`.
   Затем штамп переезжает на новое место, чтобы второй проход ничего не записал повторно.

### Поворот и зеркало — по отпечатку, не по yaw

`yaw` сущности при повороте блюпринта **не поворачивается**, поэтому ориентация определяется иначе:
блоки вокруг маркера (отпечаток) сравниваются с записанным в `FP` во всех **восьми** вариантах
(4 четверти × зеркало), побеждает лучший результат. Ничья → `IDENTITY` (без поворота). Если совпало
меньше 60 % блоков — постройка не та, **не пишется ничего**, в лог уходит строка с числом совпавших
блоков. Зеркало применяется **первым**, затем поворот на четверть: `(1,0,0)` → t0 `(1,0,0)`,
t1 `(0,0,1)`, t2 `(-1,0,0)`, t3 `(0,0,-1)`, t4 `(-1,0,0)`, t5 `(0,0,-1)`; `y` не меняется никогда.

### Краевые случаи

* дверь считается по **нижней** половине — один граф на дверь, а не два;
* двойной сундук — **две** записи (каждая половина со своим графом);
* **обрезанная вставка** (маркер вставился, а блоков-хозяев нет) — не раскладывается ничего, ждём молча;
  следующий проход попробует снова, как только блоки появятся;
* конфликт на месте вставки — **вставленная копия перезаписывает** старое, без вопросов (выбор автора).

### Что остаётся редактируемым

Якорь — **только транспорт**. После раскладки каждый граф живёт в своём обычном хранилище по
`позиция_маркера + смещение`, и редактируется жезлом НПС ровно как раньше: блок, дверь (с замками) и
сундук — по отдельности, независимо друг от друга. Даже если один маркер обслуживает две постройки,
каждый граф после вставки — самостоятельная запись.

## Ручные ручки (на случай, если автоматика не видит)

| команда | что делает |
|---|---|
| `/settledlands anchor seal` | запечатать постройку, в которой стоит игрок, прямо сейчас |
| `/settledlands anchor here` | где ближайший якорь и есть ли он вообще у этой постройки |
| `/settledlands anchor list` | что именно несёт ближайший якорь |

Плюс **жезл НПС по телу** (`NpcGraphAnchorInteract420`, `PlayerInteractEvent.EntityInteract`,
`EventPriority.LOWEST`): по маркеру — запечатать, по обычному телу — «у этой постройки должен быть якорь
здесь». Клик отменяется **только если якорь действительно что-то записал**; иначе клик идёт дальше как
раньше (одержимость, инвентарь и т. п.). Это важно: слушатель не перехватывает чужие нажатия.

| класс | что внутри |
|---|---|
| `NpcGraphAnchorCore420` | **правило и только правило**: упаковка/распаковка NBT, восемь поворотов, счёт отпечатка, раскладка. Из классов игры знает только `BlockPos`, `CompoundTag`, `ListTag` — проверяется гейтом |
| `NpcGraphAnchorFiles420` | мир: четыре хранилища (каждое открывается отдельно — битый файл стоит только своего вида), сбор графов вокруг маркера, запись |

| `NpcGraphAnchorEvents420` | один `ServerTickEvent.Post` с шагом `PERIOD`, без работы при пустом сервере |
| `NpcGraphAnchorInteract420` | жезл по телу (см. выше) |
| `NpcGraphAnchorCommand420` | `/settledlands anchor seal\|here\|list` через `RegisterCommandsEvent` |

Ни одного миксина не добавлено и не удалено, `mixins.json` не тронут, новых блоков и новых хранилищ нет.

## Найденная и исправленная ошибка (важно для следующих сборок)

Первая версия заглушки `com.mojang.brigadier.CommandDispatcher#register` была объявлена как
`register(ArgumentBuilder)`, тогда как в brigadier (и в самом jar, в `ModCommands#register`) это
`register(LiteralArgumentBuilder)` — `RootCommandNode` принимает только литералы. Класс скомпилировался,
но вызвал бы `NoSuchMethodError` в игре при регистрации команды. Это ровно ошибка сборки 280
(`Entity#hasLineOfSight`). Поймал гейт `check_mixin_class` фазы D: заглушка теперь повторяет настоящую
сигнатуру, и `BuiltInRegistries.BLOCK`/`ENTITY_TYPE` объявлены с тем же типом `DefaultedRegistry`, каким
их видит уже работающий в игре код мода.

## Как проверить в игре (короткий сценарий)

1. Поставить постройку, повесить на блок/дверь/сундук графы жезлом НПС.
2. Постоять рядом пару секунд — в логе появится строка `anchor: ...` о запечатывании.
3. В Axiom скопировать постройку **вместе с сущностями** (`Copy Entities` включён!), вставить в стороне;
   при желании — `Ctrl+R`/`Ctrl+F` (поворот/зеркало).
4. Постоять рядом пару секунд, затем `/settledlands anchor list` — графы на месте; жезлом открыть блок,
   дверь и сундук и убедиться, что каждый граф редактируется и работает отдельно.

Если шаг 3 сделан без сущностей (`Copy Entities` выключен), маркер не переедет и графов на новом месте
не будет — это ограничение копировального инструмента, а не мода. В логе будет видно, что маркер
не появлялся.
