# Settled Lands 0.8.0 Build 442 — Исправление перекоса шансов при лимите веса ящика, честная колонка «Шанс» и настройка узла в редакторе

База: `settledlands-0.8.0-build441-rarity-crate-weight-and-silent-anchor.jar`

## Почему на скриншоте выпадали 3 стейка при редкости 1

Здесь наложились сразу две причины — ошибка расчёта в генераторе остатков веса и неочевидное отображение ограничений узла:

1. **Перекос в алгоритме заполнения остатка веса ящика (`LootPool436.rollDrops`)**:
   - В Build 441 при каждом броске из списка претендентов заранее выбрасывались все предметы тяжелее *оставшегося* свободного веса ящика.
   - В итоге, когда тяжёлый предмет (например, Алмаз весом `90` в ящике `100`) оставлял немного свободного веса (`10`), на 2-м и 3-м бросках влезть в остаток мог **только лёгкий предмет (`Стейк` весом `1`)**, и его шанс выпада подскакивал с **`0.74%` до `100%`**.
2. **Ограничение узла `Вес ящ.: 0-30` блокировало тяжёлые предметы без честного пересчёта колонки «Шанс»**:
   - На узле графа стояло `Вес ящ.: 0-30`, из-за чего **Железный слиток (`Вес = 50`)** и **Алмаз (`Вес = 90`)** вообще никогда не могли выпасть (`0%`), а **Железный меч (`Вес = 25`)** влезал только в `~19%` случаев (при случайном лимите `25..30`), оставляя в остальных `~81%` случаев один только **Стейк (`Вес = 1`)**.
   - При этом колонка **`Шанс`** продолжала показывать доли от всего пула (`0.74%` у Стейка, `!58.8%` у Алмаза, `!14.7%` у Слитка), скрывая реальную картину (`78%` у Стейка и `0%` у Алмаза и Слитка).

## Что исправлено в Build 442

### 1. Честный ролл редкости при ограничении веса ящика (`LootPool436.rollDrops`)
- Рулетка по **`Редк.`** (стиль CS:GO кейсов) теперь всегда крутится по всем предметам, которые проходят общие настройки узла и **начальный** бюджет веса ящика (`initialWeight`), а не по суженному остатку веса (`remainingWeight`).
- Лёгкие предметы с низкой редкостью (`Редк. = 1`) больше **никогда** не подменяют собой более частые предметы и не превращаются в 100%-й наполнитель остатков: при `Вес ящ. = 100` (или без лимита веса) и `Шт = 3` Алмаз (`80`) стабильно падает чаще Меча (`35`), Меч чаще Слитка (`20`), а Стейк (`1`) сохраняет свои честные `~0.74%` на бросок.
- Если случайно выбранный предмет не помещается в оставшийся вес ящика (`chosen.weight > remainingWeight`):
  - в режиме с явным лимитом **Шт** (`Шт = 3`) этот бросок пропускается без перекоса вероятностей остальных слотов;
  - в режиме заполнения **по весу** (поле **Шт** пустое, например `Вес ящ. = 40` для 2 мечей по 20 или 4 книг по 10) наполнение ящика останавливается.

### 2. Точный эффективный шанс в колонке «Шанс» (`LootPool436.computeEffectiveChancesPct`)
- Добавлен точный аналитический расчёт вероятности первого дропа с учётом текущих ограничений узла (`Редк.<=` и `Вес ящ.`, включая диапазоны вроде `0-30`).
- В таблице редактора **`LootPoolEditorScreen440`**:
  - предметы, которые полностью не помещаются в лимиты узла, показываются красно-оранжевым как **`0% !`** (с точной причиной при наведении: например *«Отсечён: вес 90 > макс. Вес ящ. (30) -> шанс 0%»*);
  - предметы, чей реальный шанс сильно искажён отсевом других позиций (как Стейк при `Вес ящ.: 0-30`), подсвечиваются жёлтым как **`78.0%*`** с подсказкой сравнения реального и базового шансов;
  - при достаточном весе ящика (или без ограничений) отображаются чистые зелёные шансы (`0.74%`, `14.7%`, `58.8%`, `25.7%`).

### 3. Редактируемые параметры узла прямо в шапке редактора + заметные предупреждения
- Если редактор открыт из узла графа, под строкой файла добавлена компактная панель параметров узла: **`Узел:  Редк.<= [ ]   Вес ящ.: [ ]   Шт: [ ]`**.
  - Лимиты узла можно поменять (или очистить `Вес ящ.` для отключения ограничения веса) **сразу не выходя из редактора**, и колонка **`Шанс`** с тестовым броском **`Тест`** пересчитаются мгновенно.
- При блокировке части предметов настройками узла вверху и рядом с тестовым дропом показывается оранжевое предупреждение **`! Отсечено узлом: N/M`**.
- В инспекторе узла (`LootPoolInspectorMixin436`) подсказки полей редкости/веса заменены на `любая` (пусто = без ограничений), чтобы случайно не сбивать на ввод `0-100` / `40` без необходимости.
